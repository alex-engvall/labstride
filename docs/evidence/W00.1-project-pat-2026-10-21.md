## Credential and test boundary

The operator explicitly supplied `GH_PROJECT_PAT` in an installation-local dotenv file and authorized mode `0600`. File ownership, regular-file type and absence of a symlink were checked; mode was changed from `0644` to `0600` before use and verified afterward. Only the named literal variable was parsed. The file was not sourced, other variables were not exported, and no shell interpolation was performed.

`GET /user` returned the expected account `alex-engvall`, header `X-OAuth-Scopes: project`, REST version `2022-11-28`, and token expiration `2026-10-28T05:00:35Z`. Writes were blocked locally unless the identity matched and the reported scopes contained `project` without unrelated grants. The token was held in process memory, never printed and never copied into source files, reports or the installation-local bootstrap record. The bootstrap stores only a credential reference and non-secret verification metadata. The supplied PAT remains available for the operator's subsequent use; unlike temporary App test tokens it was not revoked.

Tests targeted only personal Project #8 and the previously owned, closed public [fortnox-mcp issue #80](https://github.com/alex-engvall/fortnox-mcp/issues/80). No new repository issue, source change, branch, PR, workflow run, deployment or Fortnox API action was created. Existing work items and start/status fields were not edited.

The provider scope covers accessible user/organization Projects and is not restricted by GitHub to #8. The probe's selected target was #8; an implemented adapter still needs its own validated target configuration. Private Projects and private issue-backed items were not tested.

## Reproduction

Use the dedicated PAT, not the owner's general CLI login or an App token. Read it through a parser that selects one named literal value without evaluating the dotenv file. Validate file mode, authenticated account, exact reported scopes and expiry before effects. Keep the value out of command arguments, log output and persisted request bodies. The tests used Python `3.13.5` standard-library HTTP against GitHub.com, REST `2022-11-28` and the live GraphQL schema.

Query `user(login:$owner){projectV2(number:$number)}` with configured owner/number and resolve field and option IDs. Read `fields` and `items` with cursors until complete. For schema inspection, send one `__type(name:$name){fields{name description}}` request per type. The [initial probe report](W00.1-github-access-2026-10-21.md) includes the field-query and mutation shapes.

For the draft, invoke `addProjectV2DraftIssue` once with a new unique marker, persist the returned ID, then independently query `node(id:$item)` with `project`, `type`, `content` and `fieldValues`. Only operate on the known fixture. Set Priority using `updateProjectV2ItemFieldValue` with `value:{singleSelectOptionId:$option}`, inspect `fieldValues` and match the stable field ID and option ID, clear with `clearProjectV2ItemFieldValue`, and verify the value is absent. Delete the exact new item with `deleteProjectV2Item` and enumerate the Project to prove absence.

For the public issue fixture, resolve `repository(owner:$owner,name:$repo){issue(number:$number){id state title body author{__typename login}}}`. Confirm its ownership marker, closed state and absent Project membership before calling:

```graphql
mutation($project:ID!,$content:ID!){
  addProjectV2ItemById(input:{projectId:$project,contentId:$content}){
    item{id type}
  }
}
```

Persist the new membership ID, repeat the same set/read/clear/read sequence and remove only that membership, preserving the repository issue. Never remove a membership that predated the probe. A lost create/update/remove response requires reconciliation from recorded IDs/markers, not a replay. Compare the complete Project membership set before and after; do not remove unrelated new items to force the count to match. Detailed non-secret receipts are stored installation-locally outside the source workspace.
