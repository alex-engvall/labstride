# W03.3 — Recipe-owned runtime implementation evidence

Requirement: LS-SSH-005. Related case: AC30 (partial runtime/configuration coverage; cleanup execution remains W05). Implementation contract and plan: [recipe-owned runtimes](../36-recipe-owned-runtimes.md).

## Accepted decisions and adopted design

Application runtimes are optional and recipe-owned (D05). Concurrent issues retain separate workspaces/branches (D11); a source-only installation requires no agent. The implementation adds a separately pinned public action and a versioned target driver protocol. The core retains generic claims, effect boundaries, outbox and resource-result transactions; it does not select a framework, database engine, control panel, deployment workflow or cleanup timer.

## Executed environment

Tests run on Linux x86_64, Node 24.22.0 and Git with the real invoking UID and filesystem ownership. The default filesystem sandbox remaps protected ancestors; the pre-existing workspace ownership tests correctly reject that environment. The recorded functional results use execution outside that remapping, with only test-created temporary checkouts/databases/processes. They do not change the enrolled pilot or any of its five retained workspaces.

## Observable behavior

- Source-only Git checkout succeeds without opening the runtime registry or starting an app/session.
- Two public profiles run the same reviewed, integrity-pinned example driver. One creates a real SQLite database; the other starts a real Node HTTP process on an allocated loopback port and returns a correlated HTTP response. Two independent issue/workspace identities have distinct databases, resource names and HTTP ports.
- Original operation, source receipt digest, exact recipe pin, generated namespace, resource locators and cleanup action/version/trigger are retained in the protected runtime registry and operation result. Different cleanup triggers require no core change; no cleanup is executed by this slice.
- Concurrent/duplicate requests retain one allocation. A different operation cannot claim the same workspace/recipe namespace. Recipe-key ordering cannot create another namespace. Source edits and later SQLite user data survive inspection.
- Actual helper processes are killed at durable intent, driver completion and committed receipt boundaries. An incomplete intent stays unknown and never reruns create. Complete driver evidence recovers the same resources even when the helper's terminal receipt was not committed.
- An actual helper SIGKILL after HTTP creation recovers the original live process and port. A dead HTTP process without a committed helper receipt remains unknown; neither inspect nor a duplicate create restarts it. A committed creation receipt is historical evidence, not a health guarantee.
- The public action runs through ordinary coordinator claims/effects/resource transactions. A discarded real recipe reply plus coordinator close/reopen recovers one original operation and adds its resource inventory once. Actual coordinator SIGKILL before helper dispatch retains uncertainty without inventing a runtime; SIGKILL after the helper reply recovers the original resource without another create. A compiled/pinned composition invokes the real installed helper in a separate process; that test substitutes only a local subprocess transport and does not qualify SSH.
- Wrong source/run/workspace/recipe/digest/root, unknown source operation, injected inputs and expired new operations cause no runtime creation. Foreign directories/symlinks, changed root identity, unsafe/altered drivers, unmanaged SQLite files and malformed/oversized/timed-out/uncorrelated driver replies cannot become successful registrations. Artifacts are rechecked after caching.
- A v3 helper installation retains the original v1 and v2 reply formats/capability lists. The existing source registry remains schema 2; runtime data uses a separate protected schema-1 database. All uncertain resources remain retained.

## Open qualification gates and recovery limits

LS-SSH-005 is implemented with actual Linux resource/recovery evidence. It is not marked fully verified: this account cannot run the root-operated isolated OpenSSH suite, and no W03.3 release has been installed on the enrolled pilot. The new real-SSH runtime reply-loss/legacy-compatibility test exists in `tests/ssh-transport.test.mjs` and must pass in that qualified environment. Earlier W03.2 SSH evidence is not substituted for this new path.

Full AC30 remains `not_run`: its LS-CLN-001 cleanup trigger/effect is not implemented here. General workflow advancement belongs to W04, installed polling/service operation to W06 and deletion to W05. No deployed application, public route, automatic health repair, power-loss durability, other OS or multi-tenant isolation is qualified. The HTTP example serves infrastructure identity only and never executes source. Privilege separation on a live v3 installation still needs its own qualification; a real single-UID test is not that proof.

Rollback retains both registries, original pins/driver versions, unknown outcomes, checkouts and application resources. Keep a v3-compatible inspector available; reverting code or SQLite backups does not undo a created database/process. Tests stop/remove only their own disposable fixtures after observing their identities. There is no production deletion, implicit process-stop, down migration or new operator SSH access in this delivery.
