# W03.3 — Recipe-owned runtime implementation evidence

Implementation: [PR #63](https://github.com/engshort/labstride/pull/63). Requirement: LS-SSH-005. Related case: AC30 (partial runtime/configuration coverage; cleanup execution remains W05). Implementation contract and plan: [recipe-owned runtimes](../36-recipe-owned-runtimes.md).

## Accepted decisions and adopted design

Application runtimes are optional and recipe-owned (D05). Concurrent issues retain separate workspaces/branches (D11); a source-only installation requires no agent. The implementation adds a separately pinned public action and a versioned target driver protocol. The core retains generic claims, effect boundaries, outbox and resource-result transactions; it does not select a framework, database engine, control panel, deployment workflow or cleanup timer.

## Executed environment

Tests run on Linux x86_64, Node 24.22.0 and Git with the real invoking UID and filesystem ownership. The default filesystem sandbox remaps protected ancestors; the pre-existing workspace ownership tests correctly reject that environment. The recorded functional results use execution outside that remapping, with only test-created temporary checkouts/databases/processes. A separately authorized isolated release subsequently ran on the enrolled Linux pilot. Its state/root/policy, pinned artifacts and loopback SSH server were separate from the existing installation; the original five workspaces, registry, policy and launcher were retained unchanged.

## Observable behavior

- Source-only Git checkout succeeds without opening the runtime registry or starting an app/session.
- Two public profiles run the same reviewed, integrity-pinned example driver. One creates a real SQLite database; the other starts a real Node HTTP process on an allocated loopback port and returns a correlated HTTP response. Two independent issue/workspace identities have distinct databases, resource names and HTTP ports.
- Original operation, source receipt digest, exact recipe pin, generated namespace, resource locators and cleanup action/version/trigger are retained in the protected runtime registry and operation result. Different cleanup triggers require no core change; no cleanup is executed by this slice.
- Concurrent/duplicate requests retain one allocation. A different operation cannot claim the same workspace/recipe namespace. Recipe-key ordering cannot create another namespace. Source edits and later SQLite user data survive inspection.
- Actual helper processes are killed at durable intent, driver completion and committed receipt boundaries. An incomplete intent stays unknown and never reruns create. Complete driver evidence recovers the same resources even when the helper's terminal receipt was not committed.
- An actual helper SIGKILL after HTTP creation recovers the original live process and port. A dead HTTP process without a committed helper receipt remains unknown; neither inspect nor a duplicate create restarts it. A committed creation receipt is historical evidence, not a health guarantee.
- The public action runs through ordinary coordinator claims/effects/resource transactions. A discarded real recipe reply plus coordinator close/reopen recovers one original operation and adds its resource inventory once. Actual coordinator SIGKILL before helper dispatch retains uncertainty without inventing a runtime; SIGKILL after the helper reply recovers the original resource without another create. A compiled/pinned composition invokes the real installed helper in a separate process; that test substitutes only a local subprocess transport and does not qualify SSH.
- Wrong source/run/workspace/recipe/digest/root, unknown source operation, injected inputs and expired new operations cause no runtime creation. Foreign directories/symlinks, changed root identity, unsafe/altered drivers, unmanaged SQLite files and malformed/oversized/timed-out/uncorrelated driver replies cannot become successful registrations. Artifacts are rechecked after caching.
- A v3 helper installation retains the original v1 and v2 reply formats/capability lists. The existing source registry remains schema 2; runtime data uses a separate protected schema-1 database. All uncertain resources remain retained.

## Installed Linux/SSH qualification

The complete pilot regression passed **509/509 tests, zero failures/skips**, including the new actual SSH runtime reply-loss/legacy-compatibility test. The same 30 focused tests also passed as the actual helper UID. The pilot checked all 66 generated contracts and ran the pinned TypeScript compiler directly; its existing npm launcher lacks the ordinary bin PATH. The code/artifact hashes match the locally tested implementation; see the sanitized receipt for the exact implementation revision and profile digest.

A protected, explicitly operator-admitted composition used the public compiler fixture descriptor and the real configuration/policy/store/worker, installed action artifacts and authenticated strict-host-key SSH. This is not GitHub event admission, a new AC36 proof or W04's general workflow runner. It used only an allowlisted public GitHub source at an exact SHA and no agent/session account or source credential. Two independent complete cases first created source-only checkouts, then explicitly scheduled the optional recipe actions in order.

Each complete case received one actual SQLite database and one actual loopback HTTP service: four independent runtime namespaces and six correlated source/runtime inventory entries. Effective coding UID checks verified exact source SHA, distinct branches/Git databases, source write access and protected parent/marker boundaries. After writing coding edits, the helper returned the same source proof without resetting them. Direct read attempts verified that coding cannot read either registry, coordinator state or the SSH private key; helper cannot read coordinator state/key; coordinator cannot read helper/runtime registries.

The first database action's genuine SSH reply was discarded and ordinary inspection recovered the same recorded resource. For the HTTP phase, the test-only protected supervisor discarded the selected real create/inspect replies, held that original operation unknown, and verified its own coordinator's UID, executable, start identity and ancestry before sending SIGKILL through a pidfd. A fresh coordinator inspected that same original operation over SSH and registered its resource once. Another process opening and duplicate scheduling retained all four successful runtime operations, their resource inventory and coding edits. Independent HTTP reads returned the original binding digests; the two SQLite databases held the expected ownership rows and distinct filesystem identities.

### Retained incomplete operator cases

An earlier mixed operator phase recorded `storage_failure` and incomplete evidence. Read-only recovery and subsequent in-memory/file SQL diagnostics did not reproduce that transient; all 30 focused tests also passed under the helper UID. Its original partial database lacks a complete ready proof, and a source operation has no sufficient target creation evidence. They remain `outcome_unknown` with their original records and data. No clone/driver create was replayed, no receipt was fabricated and no alternate locator was assigned to either operation. The later complete cases were separately admitted independent test requests, not replacements for those unknown operations. This retention is not a claim that the earlier phase succeeded or that incomplete materialization is automatically repairable.

The isolated installation retains three new actual checkouts (the two qualified cases plus the earlier source checkout), one partial runtime intent and the unobserved source operation metadata. The original five workspaces and every original registry row match the pre-test baseline; policy and shared-launcher byte hashes also match. Consistent final backups are retained. After live HTTP verification, only the identity-checked test HTTP processes and isolated SSH server were explicitly stopped. All registered directories, databases, receipts and coding edits remain. The temporary operator root access was revoked, a fresh login with that key was denied and its local key files were deleted; original access entries remain.

## Qualification scope and recovery limits

LS-SSH-005 is verified for the recorded installed Linux/SSH creation/recovery profile. The root-operated transport suite and actual helper/coding/coordinator isolation are separate from the earlier single-UID local tests. The HTTP receipt attests creation; the explicit test teardown does not advertise ongoing service health or activate the shared helper launcher.

Full AC30 remains `not_run`: its LS-CLN-001 cleanup trigger/effect is not implemented here. General workflow advancement belongs to W04, installed polling/service operation to W06 and deletion to W05. No deployed application, public route, automatic health repair, power-loss durability, other OS or multi-tenant isolation is qualified. The HTTP example serves infrastructure identity only and never executes source.

Rollback retains both registries, original pins/driver versions, unknown outcomes, checkouts and application resources. Keep a v3-compatible inspector available; reverting code or SQLite backups does not undo a created database/process. Disposable test fixtures are removed only by their own tests; the registered operator-probe resources above are retained. There is no production deletion, implicit process-stop or down migration.
