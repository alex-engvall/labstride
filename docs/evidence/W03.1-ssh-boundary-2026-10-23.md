## Decisions, implementation and evidence

The accepted plan selects an existing operator-owned pilot host, conventional OpenSSH over its existing VPN, explicit key enrollment, separate OS identities and a bounded trusted helper. HostUp provisioned only temporary bootstrap SSH access. Existing access entries, system host keys, system Node and the interactive backend were preserved. Provider names, hostnames, IPs, account IDs, literal installation paths and authentication material are omitted from the public evidence. Neither HostUp nor the VPN is a dependency of the public connector.

The [normative contract](../33-ssh-target-boundary.md) describes the implemented operator enrollment API, pinned connector/facade, helper policy and request/response schemas, root guard, durable registry and existing-worker integration. The helper supports probe, reservation and inspection only. A reservation is a durable ownership claim for later source preparation; no source directory, checkout, session, runtime or deployment was created by it. Core workspace state remains `requested`.

The [sanitized receipt](W03.1-pilot-receipt-2026-10-23.json) records actual installed-artifact/runtime digests, one retained reservation, repeated same-identity observations, account-isolation results and bootstrap revocation. It is a probe/evidence record, not a new runtime API or completion receipt. The live direct-operation IDs and configuration digest are synthetic probe identities; this is not an authorized GitHub transition or a compiled workflow admission. Configured snapshot selection and policy/admission retain their separate executable coverage.

## Actual pilot accounts and retained resources

The pilot uses three distinct OS UIDs: coordinator, unprivileged helper and coding. The release, launcher and helper authorized-keys file are root-owned. The helper key uses a fixed forced command with `restrict`; its launcher strips the environment. Helper registry and coordinator state/key material use separate private directories. The system's Node **22.23.2** and existing backend were retained; Node 24 lives in a separate pilot prefix, with its license copied alongside the runtime.

The installed connector artifact SHA-256 is `29adef1de869cb298373c401d7ada4126dca8d7112e045fdb7467c662d3fd3de`. The runtime SHA-256 is `67ca5783febb8bf85736c79fcdd92c8d6d465a0eb2a082672bcdfa76a506751c`. Separate processes running as the coordinator repeatedly probed/inspected the actual installed helper and retained the same reservation. The authoritative target registry contained exactly **one** reserved row and no source directory for that locator.

`probe_target_isolation.mjs` then executed as the actual coding UID with a clean environment. It was denied **seven reads**, **eleven writes** and write access to **four protected directories**. Protected targets included real helper policy/registry/code/authorized keys, coordinator enrollment/authentication material and synthetic coordinator policy/projection/deploy fixtures. All protected bytes stayed unchanged. A fabricated agent-writable approval/completion/ownership report remained an ordinary coding-owned file; directly launching the helper failed without privileged output.

No actual production projection/deploy secret was used. No interactive provider/session was started or enrolled as the new coding account. The existing backend remains outside that account's isolation proof; later session integration must verify its effective execution identity. Root/operator authority is outside the coding-user boundary.

The pilot, its restricted helper authentication key, protected policies and original reservation are retained for #22. The bootstrap key's exact live access entry was revoked through HostUp. A fresh inventory matched the three original entries/revision; the revoked key subsequently failed an actual SSH login. Only that task's two local key files were removed. The inactive public-key library record is not live access. No system restart, host-key rotation, existing-service replacement, merge or deploy occurred.

## Acceptance, remaining gates and recovery

**AC06 and AC07 passed for the tested profile.** LS-SSH-001/002 and LS-SEC-001 are `implemented` with the scoped code, live target behavior and identity-separation evidence. They are not globally verified. #21's boundary scope is ready for review and closure on merge; issue closure itself is not acceptance evidence.

Full **AC19** remains `not_run`: safe cleanup movement/deletion, concurrent writers, quiescence and tombstones belong to W05. Full **AC35/AC36** remain `not_run`: combine authorized GitHub generations/projection conflicts, real source workspace identity and the actual enrolled client in #22 and the owning W01/W02 integrations. LS-SSH-003/004 and runtime/resource namespaces in LS-SSH-005 remain #22/#23. W03 stays `in_progress`.

After uncertain dispatch, retain the original operation/profile and inspect only. Missing or denied inspection does not grant replay. A changed key/revision, root identity or protected policy blocks effects until an operator reconciles the original identities. The target/enrollment databases are separate schema-v1 stores; no coordinator migration was introduced. There is no down migration, automatic downgrade/rollback, force path adoption or cleanup timer. Removing the bootstrap key limits access without deleting the retained pilot state.

Additional checks passed: 48 schema-derived declarations plus TypeScript, four Python tests, 34 schema/example roots with rejection checks, the regenerated readable checklist and `git diff --check`. These checks supplement the behavior evidence; they do not qualify unexecuted integration environments, public distribution or disaster restore.
