# W04.4 local deployment ordering evidence — 2026-10-24

This records implementation and controlled local verification for issue #27, LS-DEP-005 and the bounded AC15 slice. The operator explicitly approved the implementation plan in the same session. The accepted completion choice allows a superseded step to advance only when independent evidence proves its confirmed actual merge is included in the current verified successor. Supersession never rewrites the earlier deployment as verified.

The [lifecycle specification](../07-lifecycle-and-recovery.md) and [deployment contract](../19-deploy-and-recipes.md) distinguish accepted behavior, adopted design, local implementation evidence and remaining live verification gates.

## Implemented behavior

- Queue creation persists operation/source identity, a coordinator-owned monotonic sequence and the expected verified predecessor. Versioned schemas and generated TypeScript declarations describe ordering, comparison and successor evidence.
- Verification advances the target/environment pointer atomically with operation/deployment completion and lock release. Dispatch and runner authorization recheck ordering, target-pointer revision, recovery epoch, original claim and existing policy/hold conditions.
- Independently compared immutable source revisions distinguish forward descendants, ancestors, identical revisions and divergent histories. A lower queue sequence cannot overwrite a newer verified sequence. A later-queued ancestor also cannot roll back the target. Unknown or divergent evidence blocks dispatch. Workflow-only enrollment cannot bypass an ordered target.
- Only operations without a dispatch intent become `superseded`. Their coordinator claim is released atomically, while their original deployment remains superseded and their bound result reports `deploymentVerified: false`. Dispatched or possibly completed effects retain their original locks and identities. No response loss, job transition, retry or lease expiry permits replay.
- A downstream deployment uses the confirmed actual merge SHA. Separate successor fulfillment requires that merge record, repository-bound containment, the current successor's finalized verification evidence and a fresh healthy observation of the same resource/revision. Missing proof blocks advancement; read-only reconciliation continues. Advancement atomically consumes the exact proof; later sample expiry or target changes cannot resurrect a completed step. Cancellation can terminate the waiting run without deployment or invented proof. W05 retains cleanup execution and its additional eligibility gates.
- Migration 17 preserves prior migration checksums and record payloads, expands state constraints and adds ordering/evidence tables. It does not invent order or current-target evidence for historical dispatches. Legacy deployment targets block new effects pending separately qualified recovery. Existing effects remain observable.
