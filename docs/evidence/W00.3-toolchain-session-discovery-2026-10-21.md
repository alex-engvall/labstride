## Node/SQLite process-crash probe

A new disposable database used WAL, `synchronous=FULL` and foreign keys enabled. One synthetic row was committed. The child inserted a second row in a new transaction and killed itself before commit (`-9`). A fresh Node process reopened the DB: SQLite `3.53.4`, journal `wal`, synchronous `2`, foreign keys `1`, exactly the committed row and `quick_check=ok`.

This verifies a bounded runtime primitive on the observed filesystem. It does not implement coordinator intent/outbox/claim recovery, test power loss or storage failure, or pass W01 acceptance. No real application database was used.

## Existing Codex backend and protocol

The running process executable matched the installed Codex binary, SHA-256 `399ff69c431c066e40de318fba45c2b07f45a76b19939d247ee4828fc70c4215`. Its CLI generated 318 regular JSON-schema files, 452 with experimental fields and 747 TypeScript files. Those are Codex protocol artifacts, not generated Labstride contracts.

`codex app-server daemon version` confirmed the existing daemon running at `0.163.0`. A sandboxed socket read initially failed with `Operation not permitted`; approved execution outside that sandbox succeeded without restarting anything. This was an executor restriction, not a missing login.

An independent bounded WebSocket client verified HTTP Upgrade/accept digest and requested only `initialize`, `thread/list`, `thread/read` and `hooks/list`. The list used the checkout filter and `useStateDbOnly=true` to avoid default metadata scan/repair. It matched the selected current thread before a metadata-only read (`includeTurns=false`).

This establishes access to the same existing session backend rather than a second daemon. App adoption of a Labstride-created session and retention of the same operation/workspace/session across recovery remain integration gates. The operator's manual verification is preserved without presenting it as those tests.

Stable and experimental `TurnStartParams` require `threadId` and `input`; neither exposes the expected-last-turn/human-activity-revision preconditions required by Labstride. `parentTurnId`/`rootTurnId` describe attribution and are ignored when input joins an active turn. `TurnSteerParams` requires `expectedTurnId`, checking an active turn rather than the complete idle/new-turn/human-activity condition. This is schema inspection, not a live stale-write rejection or concurrency test. Atomic human-priority continuation remains unsupported by the inspected interface until stronger capability is demonstrated. A read followed by a write and additional credential scopes cannot supply that guarantee.

Official [app-server documentation](https://learn.chatgpt.com/docs/app-server) describes thread lifecycle and active-turn steering. [Hook documentation](https://learn.chatgpt.com/docs/hooks) describes definition-specific trust and lifecycle events. Hook availability does not prove delivery, normalization, deduplication or durable acknowledgement; no hook was enabled. A future optional hook needs a versioned envelope and the operator's review/trust of its exact definition before a live delivery probe.

## Contract and validation findings

The pinned validator accepted the existing manifest, rejected protocol major `2`, and accepted minor `999` and an unknown capability string. These results verify static syntax constraints. They do not verify a negotiation algorithm, optional-versus-required capability handling or rejection before module execution.

There is no extension loader/application source, complete set of typed family/method/result envelopes, Labstride schema-to-TypeScript build or altered-package loading fixture. Configuration examples carry version/integrity values, but no loader verifies an artifact before import. Direct SSH/action results still need independent result envelopes without fabricated GitHub workflow identity. AC22 remains `not_run`.

**Format-check gap:** a fresh environment installed from exactly `requirements-docs.txt` had neither a registered `date-time` nor `uri` checker. `FormatChecker()` accepted an intentionally invalid string for both, yet `scripts/validate_docs.py` passed its existing checks (201 local links, seven schema/example pairs, 52 requirements, eight packages, 36 acceptance specifications). Thus that success does not establish format enforcement. #13 must supply the format dependencies or implementation, check checker availability and reject invalid formats explicitly. [jsonschema's documentation](https://python-jsonschema.readthedocs.io/en/v4.26.0/validate/#validating-formats) describes additional format dependencies. This discovery records the gap; it does not fix it.
