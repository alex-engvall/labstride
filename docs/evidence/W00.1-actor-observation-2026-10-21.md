# W00.1 — Actor attribution and observation/recovery discovery

Date: 2026-10-21. Requirement: **LS-GH-001**; related future implementation: **LS-GH-003/004/005**. Specification source: `052d4bac9a912a2cab67dffe2fda99e3d8e55458` plus local W00.1 documentation changes. Tracker: [#11](https://github.com/alex-engvall/labstride/issues/11).

**Result:** the Project-only user PAT can recover issue-backed Project membership and built-in Status events with server-supplied actor identities and event IDs. Bounded live probes demonstrated cursor catch-up, process-crash rollback of an observation checkpoint, overlap deduplication and reconstruction of a disposable observation store. Generic field history and proof of a human gesture remain unsupported by the tested surfaces. The dedicated App's current grants return an empty Project-event timeline where the PAT sees nine events. These are capability/probe results, not a working Labstride coordinator or completed acceptance scenarios.

## Scope, credentials and environment

Only public personal Project #8 and the owned, closed [fortnox-mcp synthetic issue #80](https://github.com/alex-engvall/fortnox-mcp/issues/80) were used. The existing membership was checked absent before adding one new temporary membership. No new repository issue, code, branch, PR, CI run, merge, deployment, provider transaction or session start was requested. No real work item or Project field definition was edited.

The user PAT still reported only `project`; its credential file remained `0600` and was parsed as one named literal without shell execution. Its value was neither printed nor copied. Independent App reads used tokens restricted to the selected repository, first Issues/Metadata read and then the App's complete existing grant profile. No grants were expanded. Both App tokens were explicitly revoked with HTTP `204` acknowledgements.

Environment: Python `3.13.5`, SQLite `3.46.1`, GitHub.com REST `2022-11-28`, live GraphQL schema. The disposable Python/SQLite probe ran outside the source checkout. It has no action executor, workflow broker, enrolled workspace/session, projection outbox or production coordinator. Process exits in this report refer only to child processes created for the test.

## Actor capability findings

The live `IssueTimelineItemsItemType` enum and documented `ProjectV2Event` interface expose `AddedToProjectV2Event`, `RemovedFromProjectV2Event` and `ProjectV2ItemStatusChangedEvent`. Actual reads of #80 returned event node IDs, timestamps, Project identity, `actor` type/login/stable node ID, and `wasAutomated`. Status events additionally returned old/new status strings. This is a history surface distinct from current-state item/value `creator` fields.

| Credential/surface | Observed capability | Limit |
| --- | --- | --- |
| Project-only PAT, issue timeline | All nine Project events visible, including actor identities after membership removal | Public issue-backed Project #8 case only; drafts have no tested issue timeline |
| App, Issues/Metadata read | Same filtered query returned zero events, no GraphQL errors and no next page | A successful empty response did not mean no history existed |
| App, all current approved grants | Still zero events and no errors | The difference was not just read-token narrowing; no silent fallback to the App for Project history |
| Current-state item/field values | Creator and created/updated timestamps | Not a general last-editor or per-change history |

Actual actors included the user `alex-engvall` and bot `github-project-automation`, with different stable node IDs. All nine observed events reported `wasAutomated=false`, including events whose actor was the automation bot. A newly added closed fixture was automatically assigned `Planning` by that bot; an earlier membership had received `New`. The probe did not write `Planning`, change the defaults, or interpret an automatic assignment as a request to start work. Subsequent explicit Status writes used only the neutral `New` value and no value.

The nine-event total includes three events already present before this probe and six added during it. It is not nine newly created transitions, nor a claim of complete history across arbitrary Projects or membership generations.

The user-actor Status events were also created by an automated Python process using the user's PAT. Thus a User actor and `wasAutomated=false` do not establish an interactive human action or plan approval. Actor identity is evidence for applying configured operator policy, not permission supplied by the event itself.

Status events contain status names and Project/issue context, not the configured field ID, option ID or Project membership generation. The observer must retain binding/configuration history and refresh current identity/state rather than assume that historical names or a removed/re-added membership still identify the current request.

## Live observation and crash probes

| Probe | Actual observation | What it establishes |
| --- | --- | --- |
| Missed Status observations | With observer stopped, `New -> empty -> New`; later history returned both transitions with IDs and User actor | These intermediate Status events remained recoverable although before/after current values matched |
| Missed Priority observations | `P3 -> P2 -> P3` with no intermediate observer snapshot; final value matched original; available Project timeline event-ID set did not change | Current state and these timeline types did not recover the intermediate Priority value/actor |
| Same-second ordering | Both gap Status events had `2026-10-21T04:20:59Z`; timeline returned `empty -> New` before `New -> empty`, opposite the recorded write order | Timestamp or returned list order was not a safe causal ordering rule for this pair |
| Crash after remote write | Child wrote Priority P3 then received SIGKILL before persisting its acknowledgement; fresh process found the same fixture/value; no write replay | Current-state reconciliation is available for the controlled fixture; the original persisted acknowledgement/independent causality remained absent |
| Crash before observation commit | Child inserted fetched events and new cursor in one SQLite transaction, then received SIGKILL before commit | Actual rollback retained the previous six event rows and checkpoint |
| Resume after crash | Fresh process used the retained cursor and committed the two pending events | Observation rows increased from six to eight and matched the live event-ID set |
| Overlapping full read | All history read again with event-ID uniqueness | Row count stayed eight; checkpoint and ID set stayed unchanged |
| Observe removal | Temporary membership removed; resumed history read returned its removal event | All nine events remained visible after the current Project item was absent |
| Invalid cursor | Live GraphQL returned `INVALID_CURSOR_ARGUMENTS` along with partial `data`; stored checkpoint unchanged | Error-bearing partial data must not advance a checkpoint or establish an empty history |
| Empty observation-store rebuild | New process/new SQLite file read available history from the beginning | Same nine IDs and final cursor as the existing observation store; no external mutation replay |

The observer used pages of two events, stable event IDs as a unique key, and event insertion plus cursor advancement in one transaction. This is evidence about the disposable probe and available history. It does not verify a Labstride run generation, duplicate-run prevention, outbox retry, cancellation, backup restoration or privileged-effect recovery. Rebuilding observations is not a replacement for restoring durable operation/session/ownership records.

The discarded-write-acknowledgement case was classified as **matching current state observed; original acknowledgement not persisted; no independent causal proof**. It was not converted into a generic exactly-once or safe-retry guarantee. No transient create/delete/write was automatically repeated after an uncertain response.

The writer received the API response before it was killed. This tests loss of the local durable acknowledgement, not a deliberately dropped network response. Both crash modes used process SIGKILL; neither tests machine power loss or storage failure.

## Reproduction contract

Use an approved closed synthetic issue, selected personal Project and independently configured Project PAT. Verify exact token scopes, actor identity and file permissions first. Preserve its preexisting Project membership and do not attach/remove an existing work item as a fixture. The archived probe scripts are discovery tools, not installed `labstride` commands.

The archived scripts contain the original fixture identity and local journal/database locations. Do not run them unchanged for a new probe. Prepare a separate copy with freshly validated fixture inputs and new disposable stores; retain the original archive as evidence. The source hashes establish which probe sources were retained, not an independent rerun of the reported effects.

Read the filtered timeline with a cursor, selecting concrete event fields:

```graphql
query($owner:String!,$repo:String!,$issue:Int!,$after:String){
  repository(owner:$owner,name:$repo){issue(number:$issue){
    timelineItems(first:2,after:$after,itemTypes:[
      ADDED_TO_PROJECT_V2_EVENT,
      REMOVED_FROM_PROJECT_V2_EVENT,
      PROJECT_V2_ITEM_STATUS_CHANGED_EVENT
    ]){
      pageInfo{hasNextPage endCursor}
      nodes{
        __typename
        ... on ProjectV2ItemStatusChangedEvent{
          id createdAt previousStatus status wasAutomated
          project{id number}
          actor{__typename login ... on User{id} ... on Bot{id}}
        }
        ... on AddedToProjectV2Event{
          id createdAt wasAutomated project{id number}
          actor{__typename login ... on User{id} ... on Bot{id}}
        }
        ... on RemovedFromProjectV2Event{
          id createdAt wasAutomated project{id number}
          actor{__typename login ... on User{id} ... on Bot{id}}
        }
      }
    }
  }}
}
```

Record target IDs and initial complete item/event sets. Seed an observation database using `event_id TEXT PRIMARY KEY` plus a persisted cursor. Pause the observer while writing the known fixture's values; do not infer an action from those changes. Execute the archived observer in `crash_before_commit` mode only on the disposable DB: it fetches a real page, begins a transaction, inserts events and cursor, and kills only itself before commit. Compare DB rows/cursor, run a fresh `resume`, then `overlap`. A new empty DB can repeat `resume` from the beginning to compare observation IDs.

The separate `writer_crash` mode persists a fixture-specific intent, performs one actual Priority update and kills itself after receiving the response but before persisting it. Resume by reading the existing fixture; never rerun that mode to resolve the missing acknowledgement. Record state matches without inventing write causality. Clean up only the new membership, then resume history once more. Repeat the read-only timeline query with a scoped App token to verify the observed credential difference. Inspect GraphQL errors even if HTTP status is 200 and `data` exists.

## Capability decision and owning work

With current credentials, issue-backed built-in Status and membership history are a supported **discovery path** for actor-bearing observations. General arbitrary-field/draft last-editor history is not established; the tested Priority intermediate change was not recoverable. Do not advertise `changedTo` recovery or human approval from those unsupported surfaces. Personal-Project webhooks are not the selected path: GitHub documents these Project item webhook events for organization-level Projects, while this target is user-owned. No webhook endpoint or additional account permission was enabled.

Status history availability does not by itself verify a safe `changedTo` start binding. W02 must still establish event/current-state reconciliation, authorization and request-generation semantics under reordering, renames and membership changes before enabling such a binding.

W01 must implement durable operation identity, atomic observation/checkpoint/outbox state and crash recovery in the actual coordinator. W02 must implement credential-specific capabilities, cursor overlap/reconciliation, stable target/binding/generation checks, safe handling of partial errors and actor authorization without trusting `wasAutomated` or current-state creators. Unsupported bindings must fail live preflight. W06 owns Doctor/recovery UX and AC29's complete missing-capability behavior. Initial bootstrap/import must not launch old timeline requests.

AC02, AC05, AC29, AC35 and AC36 remain `not_run`: the probe did not create real Labstride runs/workspaces/sessions or test their promised outcomes. LS-GH-001 remains `in_progress`; the report records verified provider capabilities and explicit limits, not production readiness. Continuous polling, provider retention bounds, histories exceeding the tested size, concurrent membership generations, rate-limit exhaustion/backoff, token-expiry recovery and missing external effects are still unverified. No broader token or new scope was required for the verified Status-history path.
