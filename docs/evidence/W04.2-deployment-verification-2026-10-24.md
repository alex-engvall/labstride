# W04.2 local deployment verification evidence — 2026-10-24

This records implementation and controlled local verification for issue #25, LS-DEP-003 and LS-DEP-006. The operator approved the plan in the same session and selected a replaceable read-only target observer with explicit operator recovery. The [deployment specification](../19-deploy-and-recipes.md) describes the adopted implementation; accepted choices, local evidence and remaining environment gates are separate.

## Implemented behavior

- Optional frozen deployment profiles bind recipe identity/digest, observer identity/configuration and recovery policy. Workflow-only enrollments remain compatible and cannot create verified deployments.
- Independent target reads use a versioned contract and fresh correlation ID, without expected source SHA or receipt outputs. The trusted embedding API registers observer code; remote content cannot load it or grant credentials. Missing/incompatible observers block dispatch.
- A verified deployment requires an immutable authenticated receipt, independently observed matching terminal GitHub attempt and fresh healthy target evidence of the expected application repository/SHA. Application and workflow SHAs remain distinct.
- Content-addressed evidence is durable before finalization. Operation success, deployment verification and target-lock release commit atomically after binding, conflict, hold, epoch and freshness checks. Uncertainty retries reads without repeating effects. Explicit unhealthy observations remain failures across restart before finalization.
- Failed/unknown deployments retain target/cleanup blockers. Diagnostics show evidence, recovery steps, rollback qualification and irreversible migration limits. Recovery is separately authorized and never automatically executed. A recovered target cannot rewrite the original failed deployment.
- Migration 15 is additive and invents no earlier deployment evidence. There is no down migration or generic hold-clearing/rerun endpoint.

## Local verification profile

Tests exercise the production broker HTTP server, real RSA signatures, actual SQLite transactions, a separate HTTP/SQLite target process, an owned application Git repository and real coordinator SIGKILL boundaries. The target persists release revision/health and counts effects independently; GET observations receive correlation only, never the expected SHA. The reference observer reads that service with time/size/redirect limits.

GitHub run metadata, OIDC issuer keys and dispatch replies are controlled fixtures. They are not actual Actions runs or deployed production applications. Local test setup uses only owned temporary state and checkout dependencies; installed services, trusted installation configuration and deployment credentials are unchanged.
