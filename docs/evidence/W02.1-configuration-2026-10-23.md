## Transaction and effect recovery

The tests execute the actual `startCoordinator`/`ConfigurationStore` implementation and installed loader; temporary paths/databases belong to each fixture. They do not stop an existing operator session or service.

- During configured admission, a child process stops inside the nested start transaction after lifecycle records and the run snapshot marker have been written. `SIGKILL` followed by a fresh coordinator leaves zero execution graph/decision records. Reprocessing commits exactly one original graph.
- A child process is killed after admission commit and before returning its ordinary result. Reprocessing returns the original receipt and run without calling the plan builder again. One request/run/workspace/operation/outbox and decision survive.
- Another child is killed after the effect boundary but before calling the installed action. Recovery retains the original snapshot/operation and reports `outcome_unknown`; it does not start the action again. The independent action database contains zero calls.
- A child is killed after the installed action's real SQLite effect commits but before the coordinator accepts its result. Recovery reconciles the original result from the action database. It retains the original snapshot, operation and handle with exactly one action call.
- Ordinary configuration activation produces a new revision for a different issue's new run. The older active run can still change state and keeps its original snapshot through restart. A duplicate original event returns its old receipt even after the current revision changes.
- A real v9 SQLite database is migrated to v10. Its original records, unknown operation and recorded handle remain intact; the first nine migration checksums are unchanged. Its legacy run snapshot marker stays null. The earlier v5 upgrade fixture explicitly removes v10 objects when reconstructing its historical layout; production has no down-migration.
- Boolean, number, date, null and multi-select projection values traverse the existing durable conditional-write path without string coercion. This is a synthetic provider with a real SQLite write/version check, not a claim that GitHub supplies atomic preconditions.
